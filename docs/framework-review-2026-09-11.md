# 整体框架评审（第一版）

日期：2026-09-11
评审范围：项目核心文档、经营框架、当前模块文件、实验与研究计划。

## 结论

整体方向没有根本性问题：先搭经营骨架、再用内容和人工交付验证，最后再自动化，是适合当前阶段的路径。当前框架可以继续使用，但还不能称为“第一轮链路可运行”，主要缺少闭环定义、阶段门槛、指标口径和若干模块落地文件。

## 必须修正的问题

### 1. 线性链路需要改成“主链路 + 反馈回路”

当前表达容易让人按顺序做完八个模块，但实际验证是循环的：

```text
内容/渠道 → 线索 → 客户问题 → 人工诊断/交付 → 结果与付费
   ↑                              ↓
   └──── 定位、产品、内容和流程迭代 ← 数据复盘 ────┘
```

应明确：内容反馈可以改变客户假设，交付结果可以改变产品和内容，复盘不是末端汇报而是下一轮实验输入。

### 2. 阶段 0 的完成标准与当前进度板不完全一致

框架要求八个模块都有输入、输出、指标和记录位置，但当前只有部分模块文件；“产品与成交”“交付与客户成功”“数据复盘与迭代”“客户与场景”尚未形成同等粒度的模块文档。因此当前更准确的状态是“框架已设计，第一轮闭环准备中”，不是“链路已运行”。

### 3. 研究暂停与内容测试计划存在冲突

决策记录写明：成熟项目借鉴确认前，暂停自行设计内容草稿和直接发布测试；但进度板和实验文件仍把三条内容发布作为下一步。需要二选一：

- 若研究借鉴是发布前置门槛，删除/标记内容测试计划为暂停；
- 若只要求借鉴方法、不阻塞业务实验，则明确“研究与最小发布并行”，并规定发布前只需完成哪些方法核验。

### 4. 指标目前可记录，但还不能稳定判定

“有效评论”“有效线索”“重复问题”“付费信号”“可见结果”等词尚无统一定义，也没有时间窗、分母和通过/停止阈值。至少应为每轮实验补充：

- 统计周期和归因规则；
- 事件定义及必填字段；
- 过程、行为、业务指标的分母；
- 继续、调整、停止的门槛。

播放量继续作为背景指标是正确的，但不能只说“不看播放量”，应说明它在样本量和分发异常判断中的辅助用途。

### 5. 三类主题各发一条，证据强度不足

一条内容只能作为探索性信号，不能比较主题优劣。首轮可以保留三类主题，但应将结论限定为“发现信号”，控制变量（入口、承诺、发布时间记录、跟进方式），并允许同主题复测。否则容易把题材差异、账号分发波动或表达质量误判为客户需求差异。

### 6. 缺少最小经济模型和交付容量约束

业务与定位中有资源限制，但框架没有统一记录：人工时薪/可投入时数、单次交付成本、最低可接受价格、退款/风险边界、获客到交付的容量。即使不提前定产品，也应在首次付费实验前补一个“单位经济与容量”表，否则可能验证出无法交付或不值得交付的问题。

### 7. Agent/Skill 的层级表达需统一

正文说 Agent 和 Skill 嵌入八个模块，不另起业务线；进度板却把 Agent/Skill 列成第九个模块。建议将其改名为“能力自动化层”，作为横切层，统一记录每个候选的触发条件、输入、输出、验收标准、人工审批和失败回退。

### 8. 证据与隐私规则还不够可执行

已有“脱敏”和人工核验原则，但还缺少证据 ID、原始记录位置、采集日期、授权/保存期限、谁可访问等字段。涉及私信、客户业务和平台后台时，应在模板中固定这些字段，避免后续无法复核或过度保存敏感信息。

## 建议的修订后骨架

```text
能力与约束（边界层）
        ↓
客户假设 ↔ 内容/渠道实验 ↔ 线索沟通
        ↓                 ↑
   人工诊断/交付 → 结果/付费证据
        ↓                 ↑
产品与成交 ← 数据复盘/阶段门槛
        └────→ 自动化候选（横切层）
```

## 当前最合理的下一步

1. 先解决“研究是否阻塞发布”的决策冲突，并写入决策记录。
2. 补齐客户与场景、产品与成交、交付与客户成功、数据复盘四个模块的最小文档。
3. 建立统一的实验/线索/证据字段和阶段门槛，再决定是否执行三类内容测试。
4. 暂不开发 Agent；先完成一轮人工闭环并记录耗时、判断点、结果和付费证据。
