# Cheat on Content 独立项目审计

审计日期：2026-09-12
项目目录：`D:\AIWork\projects\cheat-on-content`
项目名称：Cheat on Content / 网红作弊器
审计目的：判断这个项目实际解决的问题、闭环结构、本人能力证据、可迁移能力和旧逻辑风险；不把仓库宣传文案或第三方项目数据当作发起人的商业结果。

## 1. 结论先行

Cheat on Content 是一个面向内容创作者的**内容判断校准 Skill/工作协议**。它试图解决的不是“不会写内容”，而是：

> 创作者发布内容时凭感觉下注，发布后只看数据却没有把预测、实际表现和原因系统地对账，因此长期没有形成自己的判断能力。

它把工作组织成：

```text
内容草稿
→ 按 rubric 打分
→ 发布前盲预测
→ 发布
→ T+3d 取得表现数据
→ 复盘预测与实际差异
→ 更新评分规则
→ 下一条内容继续下注
```

这个项目证明了发起人能够设计一套有输入、决策、结果、复盘和规则更新的内容运营系统；它提供了比“让 AI 帮我写文案”更有价值的方向线索：帮助已有业务的人建立自己的判断和反馈系统。

但是，当前仓库主要是通用协议、子 Skill、模板、脚本和安装器。被 `.gitignore` 排除的用户项目数据目录在仓库中没有可审计样本。因此目前不能确认：

- 发起人本人是否完整运行过这套循环；
- 预测是否比直觉、随机或简单基线更准；
- 是否带来稳定的内容结果或业务转化；
- 是否有外部创作者使用并付费；
- 是否适合作为第一款对外产品。

结论：**方法设计和工程能力证据 B；外部商业证据 C；直接复制为商品的结论暂不成立。**

## 3. 是否形成闭环

### 3.1 方法闭环：设计完整

项目对闭环的定义相当清楚：

```text
判断
→ 写下预测
→ 取得实际数据
→ 对账
→ 找到偏差来源
→ 调整规则
→ 继续预测
```

它还设计了几个防止自我欺骗的机制：

- 预测必须先于实际数据写入，预测段不可修改；
- 评分、预测和复盘分阶段，减少事后解释；
- rubric 升级需要全量重打历史样本；
- 观察记录要清理，当前规则与历史考古分离；
- 盲评分与主模型评分可以比较；
- 通过状态文件记录校准样本数、待复盘事项和运行健康度。

这些设计说明发起人已经理解：AI 输出只有进入可验证的业务循环，才可能逐渐变成有用的判断系统。

### 3.2 实际使用闭环：当前无法从仓库确认

仓库把 `scripts/`、`predictions/`、`videos/`、`.cheat-state.json` 等用户数据目录加入忽略，当前 checkout 中未发现这些目录或真实样本。因而只能确认“流程被设计出来”，不能确认“发起人已经持续运行”。

这不是否定项目，而是区分两件事：

- 代码、协议和模板：可以审计；
- 实际使用频率、预测误差、内容表现和业务结果：需要运行记录才能审计。

项目 README 中关于“一个月 100 万粉丝”“三个月判断准确度提升 10 倍”等表述属于项目宣传或自述，当前没有仓库内证据支持，不能纳入商业证据。

### 3.3 技术交付闭环：基本形成

工程层面已覆盖：

- 总协议和多个子 Skill 路由；
- 初始化、打分、盲预测、拍摄、发布、复盘、推荐、趋势、升级和状态等阶段；
- Markdown 模板、SQLite 迁移 schema 和状态管理；
- hooks，用于会话启动、预测不可变和事件记录；
- 对标导入、平台适配器和安装脚本；
- Codex 兼容说明，以及 Claude Code/Codex 安装方式。

因此它不是一个提示词，而是一套可安装的工作流程系统。

### 3.4 商业闭环：尚未形成

当前缺少：

- 一个外部创作者的真实任务和原始素材；
- 一轮由发起人完成的交付记录；
- 客户实际执行内容并回传表现数据；
- 内容表现或业务转化相对原方法的改善；
- 客户付费、预算、正式报价、交付验收、复购或转介绍。

GitHub 仓库结构、安装能力、开源许可证、文案和第三方热榜展示都不能替代这些证据。

## 4. 它真正提供的价值

Cheat on Content 的价值不是“生成更多内容”，而是降低以下成本：

1. 创作者不知道自己的判断是否可靠；
2. 每次发布都重新凭感觉下注；
3. 发布后的数据没有进入下一次决策；
4. 个人经验无法被记录、复盘和传给 AI；
5. 通用大模型不会持续记住某个账号的历史。

更准确的价值命题是：

> 帮助已有内容业务的人，把内容决策变成可记录、可校准、可持续改进的工作系统。

它的最终价值必须落到客户结果，例如：

- 在相同内容投入下提高有效内容命中率；
- 减少低价值选题和返工；
- 缩短复盘时间；
- 让团队形成可交接的选题和判断标准；
- 进一步带来咨询、预约、成交或留存。

项目目前只定义了流量表现的反馈，尚未证明它能稳定连接到客户真正的业务结果。

## 5. AI 在其中的真实位置

AI 主要可以参与：

- 从草稿和资料中提取特征；
- 按 rubric 生成评分和理由；
- 做盲预测和反事实比较；
- 从发布数据生成复盘草稿；
- 归纳跨样本观察和候选规则；
- 辅助选题、趋势整理和内容建议。

但闭环成立的关键不在于模型能否写出一条内容，而在于：

- 预测是否真的发生在数据之前；
- 数据是否真实、可比、按统一窗口取得；
- 用户是否完成发布和复盘；
- 规则更新是否经得住历史样本检验；
- 业务结果是否比原来的方法更好。

所以它是一套“AI 辅助判断和复盘系统”，不是一个自动爆款生成器。

## 6. 主要使用摩擦

项目的设计质量较高，但客户真正使用时可能遇到明显摩擦：

- 用户要先初始化、准备 rubric、导入对标或历史样本；
- 每条内容需要在发布前评分和记录预测；
- 发布后还要在指定时间窗补充表现数据并复盘；
- 不同平台的数据字段、推荐机制和时间窗不一致；
- 内容表现受发布时间、账号基础、平台分发和偶然事件影响，难以归因；
- 早期样本少，精确播放区间容易制造虚假确定性；
- 严格的盲预测和全量重打机制提升了可信度，也增加了操作成本；
- 安装器以 shell、符号链接和用户项目目录为主要路径，对非技术创作者不够友好。

其中最关键的产品风险是：

> 用户可能认可“复盘有价值”，但不愿意长期、每条、按时记录数据。没有持续输入，rubric 就不会真正进化。

这与健康顾问中“用户忘记拍饮食照片”的问题属于同一种更一般的规律：**输入动作的持续成本会决定闭环能不能活下来。**

## 7. 旧逻辑和宣传需要重新审查

以下内容不能直接作为当前商业假设：

1. **“预测流量”不等于“改善商业结果”**。播放、点赞和评论可能与咨询、预约、成交无关。
2. **“三个月 10 倍更准”需要基线和实验设计**。至少要定义误差指标、比较对象、样本数和平台范围。
3. **参考账号拟合的 rubric 不等于客户自己的规律**。对标只能作为冷启动先验，必须被用户真实数据取代。
4. **T+3d 不一定是统一有效窗口**。不同平台和内容类型的长尾不同，窗口需要按任务定义。
5. **高分不等于高结果**。内容判断还受账号、分发、封面、时机、制作质量和执行影响。
6. **“方法论通用”仍需分场景验证**。观点视频、知识内容、本地生活引流和专业服务成交的目标函数不同。
7. **工具完整不等于客户愿意使用**。初始化和持续记录的时间成本需要真实用户试用验证。

因此，后续如果重建这套能力，第一步应先把目标从“预测流量”收窄为某一类客户的一个可验收任务，例如“减少无效选题”“提高咨询型内容的有效线索率”或“缩短内容复盘时间”，而不是直接承诺爆款或粉丝增长。

## 8. 可迁移能力

只提炼方法，不复制代码：

- 把“感觉”变成明确假设和可追踪预测；
- 在行动发生前冻结判断，防止事后合理化；
- 将输入、决策、结果、偏差和规则版本关联起来；
- 用统一窗口回收反馈，形成下一轮改进；
- 让 AI 处理资料整理、评分草稿、复盘和模式提取；
- 保留人工选择、审核、业务解释和结果验收；
- 将个人经验外化成可交接、可复盘的工作系统。

这套能力可迁移到：

- 老师或专业人士的内容到咨询/报名；
- 本地商户的内容到到店/成交；
- 顾问型服务的内容到线索筛选/诊断；
- 小型团队的内容生产、交付和客户汇报。

迁移时必须重新定义目标指标。内容播放只是上游指标，不能在所有场景中充当最终价值。

## 9. 对商业顾问主线的结论

### 能作为的证据

- **方法设计证据：B级**：形成了完整的预测—发布—复盘—规则更新协议；
- **工程组织证据：B级**：具备 Skill 路由、模板、状态、hooks、安装和迁移设计能力；
- **本人实际效果证据：C级**：当前仓库没有可核验的本人使用数据；
- **外部商业证据：C级**：未发现客户、付款、验收或复购记录。

### 与前两个项目的连接

```text
米桥：把原本不可用的数据接通
健康顾问：把个人数据转成判断和行动
Cheat on Content：把内容判断转成预测、反馈和规则更新
```

三者共同显示的能力不是某一个行业产品，而是：

> 找到影响结果的关键输入，建立结构化处理和反馈循环，再把 AI 放到资料、判断和复盘的重复环节中。

这仍然只是能力组合，尚未形成客户选择和商业产品。
