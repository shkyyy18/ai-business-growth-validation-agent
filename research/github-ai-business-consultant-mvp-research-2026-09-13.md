# AI商业顾问：GitHub 开源项目调研与最低成本 MVP 方案

调研日期：2026-09-13
项目：`D:\AIWork\projects\ai-new-media-agent`
范围：整体商业顾问框架，以及商业问题、商业画布、市场研究、客户访谈、内容、线索、交付、复盘、Agent 编排、文档处理、界面和评估节点。
状态：仅完成调研与方案设计，未开始写代码、安装依赖或引入第三方项目。

## 0. 结论先行

### 0.1 没有发现适合直接复刻的“完整 AI 商业顾问”项目

GitHub 上能找到很多 Agent 框架、研究 Agent、工作流平台、CRM、知识库和评估工具，但没有一个项目同时准确覆盖：

```text
创始人能力盘点
→ 商业问题识别
→ 商业画布
→ 客户访谈
→ 商业假设排序
→ 人工 + AI 小交付
→ 结果/付费证据
→ 复盘
→ 服务/课程/Skill/Agent 产品化
```

因此本项目不应把“某个开源 Agent”当作主体。主体应继续由本项目自己的业务规则、证据等级、文件结构和验证流程组成；开源项目只作为某个节点的技术组件。

### 0.2 最低成本、最简单的 MVP 建议

第一版不做多 Agent、自动发布、CRM、向量数据库、全自动浏览器操作或 SaaS 多租户。

建议的 MVP 是：

> **AI商业顾问个人验证工作台**：以当前 Markdown/Git 项目为事实库，用一个结构化的 Python/CLI 工作流，帮助发起人完成资料导入、能力盘点、商业画布、假设排序、访谈记录、实验卡和复盘记录。

第一版的业务输出不是“自动帮客户赚钱”，而是让你稳定得到：

1. 一份有事实/假设/证据等级区分的商业分析；
2. 一份可编辑的商业画布；
3. 一份优先级明确的客户验证任务；
4. 一份人工 + AI 最小交付方案；
5. 一份实验结果与下一步决策记录。

### 0.3 推荐的技术组合

```text
项目现有 Markdown + Git       事实库、状态、决策、实验记录
Python + Pydantic              数据结构和输入输出校验
直接调用一个 OpenAI 兼容接口    模型调用，避免一开始引入网关
MarkItDown（MIT）              PDF/Word/Excel/PPT 等资料转 Markdown
GPT Researcher（Apache-2.0）   第二阶段再接入的深度研究组件
Streamlit（Apache-2.0）        第二阶段再加的本地可视化界面
LangGraph（MIT）               工作流变复杂后再接入
Promptfoo（MIT）               有稳定提示词后再做回归评测
Langfuse（核心 MIT，ee 除外）   有真实运行后再做追踪和成本分析
```

MVP 第一轮甚至可以不引入 LangGraph、GPT Researcher、Streamlit、Langfuse 和 Promptfoo；先用简单 Python 函数和现有文件跑通一轮。

## 1. 评估标准

### 匹配度

- **高**：可以直接支持本项目某个节点，且不改变业务逻辑。
- **中**：可以提供底层能力，但需要自行设计业务规则、数据结构和界面。
- **低**：功能相近，但会把项目带向另一种产品形态，或过度复杂。

### 维护状态

本报告的维护判断基于 GitHub 公开仓库页面和 GitHub API 在 2026-09-13 的仓库元数据，包括最近推送时间、归档状态、社区规模、Issue/PR 活跃度和官方文档情况。维护活跃不等于适合本项目，也不等于 API 永久稳定。

### 许可证判断

“MIT/Apache-2.0 可商用”只表示许可证通常允许使用、修改和再发布，但仍需要：

- 保留版权和许可证文本；
- 检查全部依赖的许可证；
- 检查商标、Logo、数据源和网站使用条款；
- 不把仓库代码、模型、数据和第三方服务的许可混为一谈；
- 商业分发前进行一次正式合规审查。

本报告不是法律意见。

### 2.1 整体框架结论

最适合本项目的不是 Dify、n8n、CrewAI 或 AutoGen 的整套复刻，而是：

```text
自己的业务状态机
+ Pydantic 数据结构
+ 以后按需要接 LangGraph
```

原因：

1. AI商业顾问的难点不是“让多个 Agent 对话”，而是把事实、假设、判断、证据和下一步动作分开；
2. 业务流程需要人工确认节点，不能让自治 Agent 自动替你决定客户、价格或商业结论；
3. 项目当前处于验证期，先写业务记录和实验比先搭复杂运行时更重要；
4. LangGraph 的定位正是有状态、可恢复和支持人工介入的低层编排，未来比角色扮演式多 Agent 更贴合本项目；但第一轮简单函数足够。LangGraph 官方仓库明确提供持久化状态、人工介入和长流程执行能力，并采用 MIT 许可证。citeturn3view0turn0search1

### 3.1 资料导入与知识整理

#### `microsoft/markitdown`

- **功能**：将 PDF、PPT、Word、Excel、图片、音频、HTML、CSV 等资料转换成适合 LLM 处理的 Markdown。
- **匹配度**：高。
- **许可证**：MIT。
- **维护状态**：高；微软维护，仓库持续更新。
- **可以直接复用**：文件转换器、表格/标题/链接保留、批量导入的基础能力。
- **需要修改**：增加本项目的来源标记、文件哈希、导入时间、敏感资料提示和人工确认；不能把转换结果自动当作事实。
- **风险**：输入文件会以当前进程权限被读取；不可信输入需要隔离。OCR 额外依赖可能有不同许可证，必须单独检查。MarkItDown 官方说明其目标是为 LLM 提供 Markdown，不保证人类阅读场景的高保真排版。citeturn1search10turn1search4

**结论：直接采用，作为资料入口组件。**

官方项目说明其通过浏览器完成 Agent 任务，采用 MIT 许可，同时包含匿名 telemetry 的开关；这意味着接入时不仅要看代码许可，还要明确数据和遥测边界。citeturn1search9turn3view2

### 3.3.1 画布节点结论

本项目不应该把画布生成器当成核心产品。商业画布的核心价值在于：


因此第一版直接使用现有 Markdown 画布模板最便宜，也最符合当前项目规则。后续再将 Markdown 渲染成界面。

### 3.4.1 访谈节点结论

访谈不是 CRM 的附属字段，而是商业验证的原始证据。第一版应使用本项目已有的访谈流程和 Markdown 记录：

```text
受访者同意
→ 一次只问一个主问题
→ 记录原话
→ 标记事实/推断/未知
→ 受访者核对摘要
→ 才进入主线分析
```

CRM 只有在联系人和跟进任务重复到足以产生管理成本时才引入。

### 3.5 内容研究与内容生产

GitHub 上存在一些 AI 内容工作台和社交媒体自动化项目，例如 `inbharatai/SocialFlow`，但本次检索中其许可证信息不明确，社区规模也不足以作为商业底层依赖。

本项目当前已有 M1 内容研究与生产模板，且你已经明确：内容要独立成立，直播是自然承接，不是每条内容都强行导流。因此：

- **可以直接复用**：现有 M1 输入模板、选题、脚本、剪辑预案和人工审核流程。
- **需要补强**：来源链接、对标理由、目标受众、内容假设、发布结果、客户修改次数和是否进入拍摄/剪辑/发布。
- **不建议直接复用**：许可证不明确的小型“全自动社交媒体 Agent”；不自动发布，不把生成数量当商业证据。

内容节点的第一版不需要独立开源项目，直接由业务模板 + MarkItDown + 一个模型调用组成即可。

### 3.6 直播、评论和销售辅助

没有找到一个同时满足“中文直播评论理解、业务上下文、合规边界、人工确认、私域 QA”的成熟开源项目，因此不建议拼装一个自动销售机器人。

**第一版可以做：**

```text
人工粘贴评论/私信
→ AI 分类：咨询/异议/无关/风险
→ 依据已确认 FAQ 生成候选回复
→ 人工审核后发送
→ 记录是否被采用和结果
```

**第一版不做：**

- 自动读取直播间并自动回复；
- 自动私信陌生人；
- 自动逼单；
- 自动承诺效果；
- 自动投流和自动调整预算。

这类能力必须建立在明确的客户授权、平台接口和 QA 规则上。

此节点暂不引入外部平台，避免把业务方法论误装进一个不匹配的系统。

### 3.9 界面层

#### `streamlit/streamlit`

- **功能**：快速建立本地数据应用和管理界面。
- **匹配度**：高。
- **许可证**：Apache-2.0。
- **维护状态**：高；官方项目活跃。
- **可以直接复用**：文件上传、表单、表格、状态显示、实验面板。
- **需要修改**：业务页面、证据等级颜色、人工确认按钮、实验状态和导出格式。
- **结论**：第二阶段优先于复杂前端；第一阶段可继续使用 CLI + Markdown。

Streamlit 官方仓库将其定位为快速构建和分享数据应用，并采用 Apache-2.0 许可证。citeturn2search2turn2search9

#### `gradio-app/gradio`

- **功能**：快速建立模型演示和聊天界面。
- **匹配度**：中-高。
- **许可证**：Apache-2.0。
- **维护状态**：高。
- **可以直接复用**：聊天式输入输出、文件上传和 Demo 界面。
- **需要修改**：业务状态、记录持久化、审批和实验流程。
- **结论**：若第一版更偏“对话助手”可选；若要管理画布/实验，Streamlit 更适合。

### 3.10 模型网关与多模型切换

#### `BerriAI/litellm`

- **功能**：统一多模型接口、路由、成本和限流。
- **匹配度**：中-高，但不是 MVP 必需。
- **许可证**：GitHub API 当前没有给出单一可直接依赖的 SPDX 结论，需审计仓库和依赖后再定。
- **维护状态**：高，但 Issue 数和功能范围也很大。
- **可以直接复用**：OpenAI 兼容调用、模型路由、预算控制。
- **需要修改**：模型白名单、敏感数据策略、成本归属和失败回退。
- **结论**：第一版直接调用一个模型供应商；只有出现多模型、成本和可用性问题后再接入。

## 4. 许可证风险分级

### A 级：适合优先考虑

| 项目 | 许可证 | 使用建议 |
|---|---|---|
| LangGraph | MIT | 可以作为未来编排底层，保留许可证文本 |
| Pydantic AI | MIT | 可以作为轻量结构化 Agent 层 |
| CrewAI | MIT | 代码可用，但当前业务不需要其多 Agent 形态 |
| Browser Use | MIT | 只读、合规、人工确认地使用 |
| GPT Researcher | Apache-2.0 | 适合作为研究插件，保留 NOTICE/许可证要求 |
| MarkItDown | MIT | 适合作为文件导入器，检查额外依赖 |
| Streamlit | Apache-2.0 | 适合本地 MVP 界面 |
| Promptfoo | MIT | 适合后续评估和回归测试 |

### B 级：可以内部试用，但不宜成为商业核心

| 项目 | 原因 |
|---|---|
| Dify | 改版 Apache-2.0，有多租户、Logo/版权等额外限制 |
| n8n | Sustainable Use License，属于 fair-code/source-available，不是标准 OSI 开源许可 |
| Langfuse | 核心 MIT，但 `ee/` 目录需分离处理 |
| AutoGen | CC-BY-4.0，代码使用需处理署名和其他许可条件 |

Dify 的官方许可证明确说明其基于 Apache-2.0 但增加多租户及前端 Logo/版权限制；n8n 官方文档明确说明其 Sustainable Use License 限制使用方式，并且其自身不将该许可称为 OSI 开源许可。citeturn0search0turn0search2turn0search3turn0search10

### C 级：当前不采用

- 许可证字段为 UNKNOWN/NOASSERTION 且没有充分商业合规材料的项目；
- 归档或维护状态不确定的 Flowise；
- 星标/社区极小的画布项目作为核心依赖；
- 没有许可证的社交媒体自动化项目；
- 需要接入平台账号并自动操作的项目；
- 功能完整但会引入多租户、权限、部署和升级负担的“大平台”。

“NOASSERTION”不是法律上等于“没有许可证”，它表示 GitHub API 没有给出可直接依赖的标准 SPDX 结论；在未完成许可证审计前，不应把这类项目放入商业产品核心。

## 5. 推荐的整体 MVP 设计

### 5.1 MVP 名称

**AI商业顾问个人验证工作台 v0.1**

### 5.2 MVP 目标

不是一次性构建“会替别人经营生意的超级 Agent”，而是先把你当前最需要的闭环跑通：

```text
导入个人/客户资料
→ 结构化能力和问题
→ 生成并编辑商业画布
→ 形成少量商业假设
→ 设计客户访谈/验证任务
→ 记录人工 + AI 交付
→ 记录结果、耗时、修改和付费信号
→ 生成下一步决策
```

### 5.3 MVP 的最小节点

| 节点 | 输入 | 输出 | 第一版实现 |
|---|---|---|---|
| 项目状态 | `STATE.md`、决策日志 | 当前主线和下一步 | 直接读取 Markdown |
| 资料导入 | 简历、项目文档、课程资料 | 带来源的 Markdown | MarkItDown；纯文本先直接读取 |
| 能力盘点 | 资料和访谈原话 | 能力卡、限制和证据等级 | 一个结构化提示词 + Pydantic 校验 |
| 商业画布 | 能力、客户、问题、替代方案 | 画布 Markdown | 现有模板 + 人工确认 |
| 假设管理 | 画布和证据 | 假设排序表 | 简单评分规则，不让模型自行拍板 |
| 客户访谈 | 问题假设 | 访谈提纲和记录 | 现有 Markdown 访谈模板 |
| 实验设计 | 一个窄任务 | 实验卡、验收标准 | 现有 experiment 模板 |
| AI 交付 | 客户资料和任务 | 草稿/分析/方案 | 单模型调用 + 人工审核 |
| 结果记录 | 交付、客户反馈 | 采用/执行/结果/付费 | Markdown/JSON |
| 复盘 | 所有记录 | 下一轮动作 | 固定复盘模板 |

### 5.4 代码结构建议（获确认后再实现）

```text
src/
  core/
    models.py              # Fact, Assumption, Decision, Experiment, Client, Artifact
    evidence.py            # A/B/C 证据等级与来源
    state.py               # 当前项目状态读写
  storage/
    markdown_store.py      # 继续以项目 Markdown 为事实库
    json_store.py          # 实验运行细节和结构化记录
  adapters/
    llm.py                 # 一个 OpenAI 兼容模型接口
    document_ingest.py     # MarkItDown 适配器
  modules/
    capability_audit.py    # 能力提取
    business_canvas.py     # 画布生成和更新
    hypothesis.py          # 假设排序
    interview.py           # 访谈提纲和摘要
    experiment.py          # 最小验证任务
    review.py              # 结果复盘
  cli.py                   # “商业顾问”工作流入口
  prompts/
    capability_audit.md
    canvas_review.md
    interview.md
    experiment_design.md
    retrospective.md
```

第一版不需要数据库、队列、向量库、微服务或前端工程。

### 5.5 必须保留的人机边界

AI 不得自动完成：

- 锁定最终客户群；
- 宣称市场需求已经成立；
- 代表客户承诺收益；
- 自动报价或改变价格；
- 自动联系陌生人；
- 自动发布、自动私信或自动逼单；
- 将推断写成事实；
- 将历史案例写成当前商业证据。

AI 负责：

- 整理、提取、比较、草拟、分类、记录和复盘；
- 对缺失资料、冲突信息和风险点发出提醒；
- 根据已确认规则输出候选方案。

## 6. MVP 分阶段实施步骤

### 阶段 0：不写代码，确认设计

目标：确认本报告的边界和依赖选择。

需要你确认：

1. 是否同意“个人验证工作台”作为第一版，而不是先做完整对外 Agent；
2. 是否同意第一版以 Markdown/Git 为事实库；
3. 是否同意先只支持单用户、单项目、人工确认；
4. 是否同意暂不接 Dify/n8n/CRM/浏览器自动化。

验收：形成一份明确的技术决策记录。

### 阶段 1：现有文件工作流固化

先不引入第三方框架，使用现有项目文件完成：

```text
读取状态
→ 创建/更新能力卡
→ 创建画布
→ 生成假设
→ 生成访谈提纲
→ 生成实验卡
→ 写入结果和复盘
```

验收：用你当前个人 IP 课程案例跑通一轮，所有输出能回写项目文件。

### 阶段 2：加入最小 Python 层

加入：

- Pydantic 数据模型；
- Markdown/JSON 读写；
- 一个模型适配器；
- MarkItDown 文件导入；
- CLI 子命令或菜单。

验收：同一份输入能够稳定得到结构化输出，缺字段时能提示补充，而不是静默编造。

### 阶段 3：接入真实客户验证

只选一个窄任务，例如：

```text
将客户现有资料和内容素材整理成一批内容研究/选题/脚本初稿
```

记录：

- 输入资料；
- AI 初稿耗时；
- 你的修改时间；
- 客户修改次数；
- 客户是否采用；
- 是否进入拍摄/发布；
- 客户是否愿意继续使用或付费。

验收：至少一次真实人工 + AI 交付，有客户反馈，不把历史项目当作外部验证。

### 阶段 4：有重复任务后再加组件

按实际瓶颈选择：

- 市场研究慢：接 GPT Researcher；
- 工作流分支和恢复复杂：接 LangGraph；
- 需要本地表单和看板：接 Streamlit；
- AI 调用多、需要追踪：接 Langfuse；
- 提示词版本多、需要回归：接 Promptfoo；
- 外部系统连接重复：评估 n8n，但先做许可证和部署边界审查。

### 阶段 5：再评估对外产品化

只有当以下条件出现，才考虑对外 Agent/软件：

```text
同类客户重复出现
+ 同一窄任务反复发生
+ 输入输出边界稳定
+ 人工修改量下降
+ 客户持续采用
+ 出现明确付费
+ 交付成本可计算
```

## 7. 成本判断

### 软件和开源许可成本

按照本报告的 MVP 方案：

- 第一阶段：0 元软件成本，不引入第三方运行平台；
- 第二阶段：优先使用 MIT/Apache-2.0 组件，通常没有软件授权费，但要保留许可证并审计依赖；
- Dify/n8n 等项目不作为商业核心，以避免后续许可证和多租户成本；
- 本地 Markdown/Git 不需要购买数据库、服务器或 SaaS CRM。

### 运行成本

暂不提前锁定具体金额，因为成本主要取决于：

- 使用哪个模型；
- 每次输入资料的长度；
- 是否联网深度研究；
- 是否使用浏览器自动化；
- 是否部署云端；
- 是否保存追踪和日志。

最低成本策略是：

```text
本地运行
+ 单模型接口
+ 人工粘贴/上传资料
+ Markdown/JSON 存储
+ 只对真实任务调用模型
+ 不做 7×24 后台运行
```

### 人力成本

当前最大成本不是服务器，而是你的判断和客户验证时间。因此 MVP 应优先优化：

1. 减少资料整理时间；
2. 减少重复写作时间；
3. 减少复盘遗漏；
4. 保留你的商业判断；
5. 尽快获得真实客户采用和付费信号。
