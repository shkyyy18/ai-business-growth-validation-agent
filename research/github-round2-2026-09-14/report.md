# GitHub 第二轮核查：抖音研究、采集与转写组件

核查日期：2026-09-14。通过 GitHub API 搜索仓库、固定 commit 读取 README/SKILL、许可证和关键源码；没有安装、运行、登录或抓取抖音。仓库简介、Star 和近期提交不等于可用性或商业需求。

## 结论先行

本轮找到的不是一个成熟的“行业研究 Agent”，而是四类可组合部件：

1. **自托管采集/归档**：`Evil0ctal/Douyin_TikTok_Download_API`。源码确实有抖音作者、作品、详情、评论、搜索端点和 PostgreSQL/Redis 归档设计；但 README也显示身份池、游客身份、Cookie/风控是运行前提，且项目实际运行与平台条款、内容使用授权仍需单独核对。它是最值得继续做小范围代码审查的采集候选，不等于无风险底座。
2. **单账号风格分析**：`MooYiSaMa/douyin-creator-style-analyzer`。流程是采集→原始图片/视频帧→contact sheet→逐条观察→汇总，强调不从缩略图判断、不复制文案；方向与“先大量阅读再形成判断”相近。其采集脚本依赖 vendored downloader、PyYAML、ffmpeg/ffprobe/Pillow，仍需检查依赖许可证和真实可达性；默认“20–50条首轮”只是该作者建议，不采用为本项目固定数量。
3. **博主全量转写/知识重构**：`maom98622-netizen/douyin-blogger-analysis-skill`。设计了作品总账、视频/图文/直播回放分型、术语表、转写纠错、来源/覆盖率和停止条件；最接近“先读全，再形成行业知识库”的处理思想。但仓库没有声明许可证，不能直接复制进商业产品；README要求在浏览器登录，且全量获取和接口停止返回均未实测。
4. **转写**：`imlewc/video-to-subtitle-summary-skill` 与 `yzfly/douyin-mcp-server`。前者可用本地 faster-whisper，后者是链接解析→下载→硅基流动语音识别；它们解决“拿到视频后的转写”，不解决行业账号发现、指标口径和变现核验。前者部分抖音解析依赖第三方 API，后者仓库已标记 archived，不能作为新底座。

## 有价值但不能照搬的部分

### A. 采集与保存

`Evil0ctal` 的源码端点表明确列出 user profile、user posts、post detail、comments、general/video/user search；代码注释还记录粉丝/关注列表对游客不可用，以及身份健康、分页和内容归档。它比只看仓库 README 更接近真实工程，但项目本身自称“自愈身份池”，这不等于我们应绕过平台访问控制。我们只借鉴：稳定ID、作品详情、分页状态、失败原因、原始响应分层和归档索引。

### B. 原内容观察

`MooYiSaMa` 的规则值得合并进本项目：先建立本地素材清单，再看contact sheet，最后回到原图/视频帧；把可见文字、字幕/转写、互动上下文分开；聚合只能发生在逐条观察之后。这个思路能纠正“拿标题和点赞数就让AI判断网感”的问题。

### C. 全量处理的计数意识

`maom...` 设计了主页显示数量、实际取得数量、未知/失败作品和转录率的区分。这与本项目已有的“发现账号、实质研究账号、发现作品、取得原文、实际查看、深拆分别计数”一致，可借鉴其缺口记录，不照搬“全量”承诺。

### D. 竞品分析层

`ZJU-REAL/Easel` 的 competitor-analysis Skill 规定：公开数据与搜索降级要标来源，抖音反爬时不能承诺后台完播，样本应标“近期10–20篇、非全量”。这可以作为输出层参考，但它不是我们的采集层，也不能把10–20篇改成统一行业研究配额。

## 明确排除或降级

- `pengyueren/Douyin-Account-Analysis-Skill`：有诊断流程和114条转写的自述，但内含固定阈值（如互动量均值5倍、Help/Hub/Hero配比、若干完播基准），且依赖其他采集路线。可参考字段，不把其阈值当行业事实。
- `yzfly/douyin-mcp-server`：能从已知链接取得文案的工具方向，但仓库已 archived；需要硅基流动 API key 才转写，不支持行业发现。
- `why20261/douyin-search-tool`、同系列搜索仓库：README声称可搜爆款、最新和大量结果，但当前核查只读 README/SKILL，没有实测数据、分页、字段和服务条款；不能因“最大10000条”类描述建立可信样本量。
- `ZJU-REAL/Easel`：覆盖多个社媒运营 Skill，适合借鉴编排；不是专门抖音数据底座，且不能把 Star 或 Skill 数量当能力验证。

## 对本项目的直接决定

暂不安装第三方仓库，也不把任何仓库复制为本项目 Skill。下一步最合理的组合是：

`授权/可合法读取的数据入口` → `采集与证据索引` → `本地转写/视频实际查看` → `逐条内容卡` → `动态覆盖与反例判断` → `用户人工校准`。

GitHub 能帮我们补“采集、转写、素材整理”三个机械环节；不能替代你的行业网感、样本规模决策、爆款判断和变现核验。特别是“找得多”不等于“读得深”，而“转写很多”也不等于“看过视频结构”。

完整仓库审计元数据、固定 commit、许可证和关键文件保存在本目录；没有宣称这些项目已经端到端运行成功。
